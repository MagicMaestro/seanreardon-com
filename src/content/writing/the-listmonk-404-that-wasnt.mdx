The Listmonk admin UI returned a 404 every time I clicked Save on the CORS settings page. The 404 was Listmonk-branded — its logo, its layout, its link back to `/subscription/form`. So the bug was in Listmonk, right?

It wasn't.

I started with the obvious hypotheses. Session cookie set with the wrong path. Admin API moved to an `/admin/api/` namespace I hadn't accounted for. Apache reverse proxy stripping the PUT method. Listmonk's auth middleware misrouting unauthenticated admin requests to the public router — a pattern Listmonk has historically. A v6.1.0-specific bug.

Five hypotheses, all defensible, all wrong.

The thing that broke the case open was a single test:

```bash
curl -X PUT http://127.0.0.1:9000/api/settings
```

Direct to Listmonk's port, bypassing Apache. That returned `400 Bad Request` with a JSON body — Listmonk's route worked fine, it was just complaining about an empty payload. The same request through `https://lists.seanreardon.com/api/settings` returned the HTML 404. Whatever was breaking the request was happening between Apache and Listmonk, not inside Listmonk itself.

The actual chain, traced from there:

1. ModSecurity's OWASP Core Rule Set is enabled by default on cPanel/EA4. Rule **911100** — *"Method is not allowed by policy"* — checks the HTTP method against `tx.allowed_methods`. The default is `GET HEAD POST OPTIONS`. PUT is not in the list.
2. The PUT request scores 5. Blocking threshold is 5. ModSec blocks in phase 2.
3. Apache returns 403, which cPanel wires to `ErrorDocument 403 /403.shtml`.
4. Apache subrequests `/403.shtml` — but `lists.seanreardon.com` has no document root with files. It's a reverse proxy. So Apache forwards `/403.shtml` upstream to Listmonk.
5. Listmonk has no route for `/403.shtml`. Its public catch-all serves the branded 404.

The page said "Listmonk" because it *was* Listmonk. Listmonk was answering correctly. The error originated three hops up the stack, and the response carried the brand of the last system to touch it.

The fix was one line:

```apache
SecRuleRemoveById 911100
```

Scoped to the VirtualHost. Worth noting: ModSec 2.9.x silently no-ops `SecRuleRemoveById` inside `<LocationMatch>` blocks. I wanted to scope the exception to the API path, but the obvious-looking solution didn't work — VirtualHost-level was the only scope that took effect.

The lesson, restating something I already half-knew: when an error page is branded, that's not evidence about which system *caused* the error. It's evidence about which system *served the bytes*. Reverse-proxied stacks, error-document routing, fallback handlers — any of these can put one system's chrome on another system's failure. The diagnostic that breaks the case open is usually the one that bypasses a layer to test the layer below it on its own terms. `curl` direct to port 9000 told me more in five seconds than the five hypotheses had in an hour.

---

The fix shipped. The [newsletter signup form](/subscribe/) on this site posts directly to Listmonk's public API, and it works because of this one-line ModSec exception on the reverse-proxy VirtualHost.
